# План разработки Gastronomy v0.1

Цель: перейти от гипотезы к интерактивному прототипу, затем к ограниченному пилоту. План не означает автоматического разрешения на production-разработку.

## Принципы
1. Короткие итерации с демонстрируемым результатом.
2. Каждый этап заканчивается критериями приёмки.
3. Не строить следующий слой до проверки предыдущего.
4. Изменения — через feature branch и Pull Request.
5. PR не сливать автоматически.
6. Метрики поведения важнее количества функций.

## Этап 0. Репозиторий и инженерная база

- [ ] Сохранить старые материалы без переименования и удаления.
- [ ] Создать apps/web/.
- [ ] Добавить .gitignore, .editorconfig, .env.example без секретов.
- [ ] Закрепить Node LTS, pnpm и lockfile.
- [ ] Настроить TypeScript, ESLint, форматирование и typecheck.
- [ ] Добавить CI, Dependabot, issue/PR templates.
- [ ] Описать ветки и критерии ревью.

**Приёмка:** новый разработчик клонирует репозиторий, устанавливает зависимости и запускает приложение по README.

## Этап 1. UX и дизайн-прототип

Экраны:
1. Landing.
2. Главная с активным заданием и прогрессом.
3. Каталог заданий и фильтры.
4. Детальная страница задания.
5. Присоединение к заданию.
6. Публикация результата.
7. Лента результатов.
8. Профиль и достижения.
9. Минимальная панель модератора.

Задачи:
- [ ] Карта экранов и переходов.
- [ ] Mobile-first wireframes.
- [ ] Визуальная система и библиотека компонентов.
- [ ] Состояния empty/loading/error/success.
- [ ] Кликабельный прототип с реалистичными демо-данными.
- [ ] 5–8 usability-сессий и исправление критических проблем.

**Приёмка:** пользователь без подсказок понимает, как выбрать задание, участвовать и подтвердить приготовление.

**Приёмка:** CI проходит, миграции применяются с нуля, пользователь регистрируется и входит.

## Этап 3. Вертикальный срез — одно задание от начала до результата

1. Администратор создаёт задание.
2. Пользователь видит его и присоединяется.
3. Загружает фото и текст результата.
4. Публикация попадает на модерацию.
5. Модератор одобряет/отклоняет.
6. При одобрении начисляется XP.
7. Пользователь видит результат в профиле.

**Приёмка:** весь цикл работает с реальной БД; XP нельзя подделать с клиента или начислить повторно.

## Этап 4. Социальный слой и модерация

- [ ] Лента результатов внутри задания.
- [ ] Простые реакции.
- [ ] Комментарии с ограничениями.
- [ ] Жалобы и очередь модерации.
- [ ] Скрытие публикации и блокировка аккаунта.
- [ ] Журнал административных действий.
- [ ] Ограничения частоты публикаций и запросов.

Не добавлять личные сообщения и глобальный рейтинг.

## Этап 5. Аналитика и качество

- [ ] Серверные события.
- [ ] Воронка регистрации и первого задания.
- [ ] Публикации, одобрения и повторные приготовления.
- [ ] Когорты по неделям.
- [ ] Ручная сверка событий с действиями.
- [ ] Проверка мобильных браузеров.
- [ ] Проверка backup/restore и приватности.
- [ ] Нагрузочная проверка на пилотный объём.

## Этап 6. Ограниченный пилот

Целевой план: 100–150 квалифицированных участников, 4 недели, согласно validation plan.

Измерять activation, реальные приготовления, repeat cook, повторное участие, модераторскую нагрузку, источники привлечения, CAC и готовность платить/спонсировать.

Пороговые значения — из final decision и validation plan; это внутренние экспериментальные пороги, а не отраслевые нормы.

## Этап 7. Инвестиционное решение

GO на production только после подтверждения повторяемого поведения, управляемой модерации, канала привлечения, монетизации, правовой и технической готовности.

## Ближайшие две итерации

**A:** аудит репозитория → правила → UX flow → wireframes.  
**B:** кликабельный прототип ключевого сценария → usability feedback → обновление PRD.

Не начинать с оплаты, AI, сложной экономики, чатов, микросервисов и мобильных приложений.
